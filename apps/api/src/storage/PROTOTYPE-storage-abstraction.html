🗄️ Storage Abstraction Layer

PROTOTYPE — Gibiverse MVP · #6

Question: What should the file storage interface look like so Gibiverse can use the local filesystem during dev and swap to cloud (R2/S3) for production with a one-file change? What operations does it need, where does it live, and how does the API serve files for preview vs. download?

The Interface (the liftable module)

// apps/api/src/storage/types.ts interface StorageProvider { /** Store a file. Returns the storage key (path). */ put(key: string, data: Buffer | ReadableStream, opts?: { contentType?: string; }): Promise<{ key: string; size: number }>; /** Get a file as a readable stream. */ get(key: string): Promise<{ stream: ReadableStream; contentType: string; size: number } | null>; /** Delete a file. */ delete(key: string): Promise<void>; /** Check if a file exists. */ exists(key: string): Promise<boolean>; /** Get a URL for direct access (signed URL for cloud, /files/:key for local). */ getUrl(key: string, opts?: { expiresIn?: number; // seconds, for signed URLs disposition?: "inline" | "attachment"; // preview vs download }): Promise<string>; } // apps/api/src/storage/index.ts export function createStorage(): StorageProvider { if (process.env.STORAGE_PROVIDER === "s3") { return new S3Storage({ ... }); } return new LocalStorage({ basePath: "./uploads" }); }

Guided Walkthroughs

A student uploads a PDF, views it inline, then another student downloads it. The basic lifecycle of a resource.

The same file served two ways: disposition: "inline" for the in-browser preview (react-pdf reads this), vs disposition: "attachment" for the download button. Watch how the URL changes.

Switch the provider from local filesystem to S3 mid-session. Existing files vanish (different backend), showing the one-env-var swap in action.

What happens when you try to get or delete a file that doesn't exist? The interface should handle this gracefully: get returns null, delete is a no-op, exists returns false.
